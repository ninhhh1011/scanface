# Security and workflow review — 2026-09-13

Bounded static review of HR/auth/file services, face web proxy, Python face/security code, schema constraints and existing tests. No credentials, frame/template payloads or real people were accessed. No application data or source was changed by this reviewer. This is a finding record, not proof that the complete security test plan passed. Root implementation is addressing these findings concurrently; line references describe the reviewed version and remediation must be verified with actual regression tests.

## Ranked findings

1. **P1 — Sensitive field projection is missing from mutation responses.** `apps/web/src/server/hr.ts:96` returns the entire saved record except `password_hash`; `apps/web/src/server/workflows.ts:131` does the same. An HR account with `hr:write` and `hr:read`, but without `payroll:read`, can PATCH an existing contract title or terminate the contract and receive `base_salary`. GET correctly hides that field. A second instance affects performance: after a manager enters an unpublished score/comment into a DRAFT review, the employee's own self-comment PATCH or submit response returns those manager fields although GET hides them. **Fix:** share the existing field projection across list/detail/save/workflow results. Test both denied salary reads and unpublished assessment reads through mutations.

2. **P1 — Queued mutations retain an actor authorized before session revocation.** `apps/web/src/server/auth.ts:13` resolves session/user before business locking; `apps/web/src/server/workflows.ts:9` acquires its transaction lock without rechecking that session, and uses the original actor throughout. A mutation waiting for the HR lock may run after an account lock or role change has revoked its session. `apps/web/src/app/api/face/[...path]/route.ts:15` has the same gap when consuming attendance proofs. Python's final face transaction already rechecks its current session, so it provides an existing pattern. **Fix:** revalidate and lock the current session/user inside the write transaction after obtaining the business lock, and use the fresh actor for write authorization. Ensure revocation and mutation serialize against compatible session/user locks. Regression should queue a mutation, revoke its session, then release the lock and assert no business write.

3. **P1 — AI DB privileges are not separated from root/web privileges.** `services/ai/app/db.py:14` falls back from `AI_DATABASE_URL` to `DATABASE_URL`; reviewed infra/scripts contained no restricted-role provisioning. With this documented local fallback, face/document processing can modify HR/payroll and users using the root connection, contrary to the master boundary. **Fix:** provision explicit least-privilege AI credentials with only required read columns, face/ingestion mutations and audit insert; fail production configuration without that credential. Python tests that create temporary users/sessions need a separate test setup connection, not expanded production privileges. Root acknowledged ownership of this fix; no production grant verification was performed by this review.

4. **P2 — Payroll can lock a stale or unrelated calculation.** `apps/web/src/server/workflows.ts:107` permits timesheet reopening while linked payroll is DRAFT/REVIEW, while lines 109–112 permit payroll review/lock without rechecking the source timesheet or invalidating its old items. Trigger: calculate payroll, reopen/correct the source timesheet, then lock the previous calculation. A sibling path is PATCHing DRAFT payroll `timesheet_id` after calculation (`hr.ts:84` onwards); existing items remain and can be locked against a different source period. `calculatePayroll` lines 136–148 only upserts current employees, leaving previous items behind after an employee is archived. **Fix:** invalidate dependent unlocked calculations on source reopening or source-ID changes; require a current LOCKED source and fresh calculation before review/lock; replace the period's item set atomically when recalculating. Tests must cover all three paths.

5. **P2 — Knowledge editors inherit HR document authority.** `apps/web/src/server/files.ts:10`, `:28` and `:38` use `knowledge:write` as a general upload/read/delete override. HR can upload an unattached GENERAL/CONFIDENTIAL document; any unrelated knowledge editor with its ID can read/delete it because the employee is null and the owner mismatch is bypassed. A knowledge editor can also attach documents to HR records within their employee read scope despite lacking `hr:write`. The list endpoint's stricter scope does not protect download by ID. **Fix:** distinguish the operation context: HR document mutation requires HR authority; knowledge authority applies to authorized knowledge-version-linked files. Do not use a general knowledge capability to override private file ownership. Test an unrelated knowledge editor against an HR-owned unattached document and an employee contract attachment.

6. **P2 — OT overlap validation misses overnight regular work and becomes stale.** `apps/web/src/server/workflows.ts:61–62` checks only the assignment/window for `day(starts_at)`. For a Monday 22:00–Tuesday 06:00 shift, an OT request Tuesday 02:00–04:00 is compared with Tuesday's 22:00 window and accepted. Only draft saves run this validation; changing the assigned shift after draft creation also lets newly overlapping requests reach SUBMITTED/APPROVED. Payroll later subtracts regular overlap, so this finding concerns incorrectly approved OT rather than proof of double salary payment. **Fix:** use the current and preceding business-day windows, as the attendance function already does; revalidate the schedule-dependent range on submit/approve. Test both an overnight shift and a shift changed since draft creation.

7. **P2 — Contract termination reason is bypassed by ordinary PATCH.** `apps/web/src/server/resources.ts:16` permits contract `status: 'TERMINATED'`; `hr.ts` saves it without the required terminate reason checked in `workflows.ts:79`. Trigger: PATCH an ACTIVE contract with only that status. **Fix:** enforce the same reason/transition policy for status updates or require the existing terminate action. Test that direct PATCH cannot silently terminate a contract.

## Face review outcome and evidence limits

The inspected implementation performs actual model inference and landmark/timing checks; uses matching thresholds and distinct-identity ambiguity; encrypts templates with AES-GCM bound to employee/model/dimension; checks active employee/current session before and after inference; consumes challenges before inference; and consumes attendance proof with the attendance event in a transaction under the shared biometric lock. Delete invalidates profiles, templates, consents, pending challenges and proofs. Raw frames are excluded from validation error responses. No concrete browser-to-biometric-store authorization bypass was found in this bounded static review beyond the attendance mutation revocation race above.

Basic 2D motion can be spoofed with a suitable replay/deepfake; the model card explicitly states this limitation and does not claim certified anti-spoofing. Existing tests exercise synthetic vectors/landmarks, blank-image inference and DB protocol failures; they do not establish human enrollment success, recognition accuracy, duplicate rejection or liveness accuracy. Those remain human verification gates. No new test execution was performed by this read-only reviewer; root owns integration/regression execution and final status.
